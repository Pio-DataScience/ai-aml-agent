# Problem Brief: Semantic Ambiguity in the AML Intent Layer
 
> A self-contained problem statement for a fresh reviewer. It describes the system, the
> failure, the constraints, and every approach already considered and rejected. It
> deliberately contains **no proposed solution** — the reader is being asked to produce one.
 
---
 
## 1. System overview
 
We operate a multi-agent **AML (Anti-Money Laundering) scenario builder**. A compliance
officer describes a transaction-monitoring scenario in natural language, and the system
compiles it into an executable SQL query against a data warehouse, then deploys it as a
monitoring rule.
 
The pipeline spans **two independent microservices**:
 
**Service A — "AI AML Agent" (the service this brief is about).**
A LangGraph multi-agent system. Its first meaningful stage is the **Intent Analyst node**,
which converts the user's natural-language description into a structured intent object. That
object is then handed off to Service B.
 
**Service B — "PioTech Agent" (text-to-SQL).**
A separate, independently-running microservice that receives Service A's intent output and
compiles it into an executable Oracle SQL query. It has its own tools and its own internal
**critique node** that compares the generated SQL against the intent it was handed and
iterates. Service B is effectively **stateless** with respect to the conversation — it
receives a plan, produces SQL, and does not hold a dialogue with the end user.
 
The handoff contract matters: **Service A produces a plan/spec; Service B consumes it and
writes SQL.** The quality of Service B's output (and of its internal critique) is bounded by
the quality of the plan Service A hands it. A vague or ambiguous plan produces a
technically-valid but semantically-wrong query.
 
---
 
## 2. The data warehouse reality
 
The target is a **legacy Oracle data warehouse** with the following properties, all of which
constrain any solution:
 
- **No foreign-key constraints.** Relationships between columns and their lookup/reference
  tables are *not* enforced or discoverable via database constraints.
- **Code-heavy.** A large share of columns are coded fields (`*_CODE`, `*_CD`, `*_ID`) whose
  raw values are meaningless without joining to a lookup/reference table (e.g. a country
  column stores `400`, which means "Jordan" via a lookup table).
- **Large.** Individual fact tables can have 550+ columns. There are many such tables.
- **Lookup value sets are large and effectively uncapped.** The distinct values behind coded
  columns are not small enumerations; pre-cataloguing every (column × value) pair is
  impractical.
**A data dictionary already exists** (built and used by Service B). Three tables:
 
- `PIO_BANKBI_DICTIONARY_TABLES` — table name, `PROJECT_CODE` (which module: aml, dwh,
  collection, etc.).
- `PIO_BANKBI_DICT_JOIN_TABLES` — fact join relationships.
- `PIO_BANKBI_DICTIONARY_COL` — the important one. Columns:
  `TABLE_NAME`, `COLUMN_NAME`, `OBJECT_NAME` (the column name expanded into human-readable
  form), `COLUMN_DATA_TYPE`, `LOOKUP_TABLE_NAME` (the reference table for a coded column;
  NULL if the column has no lookup), and `COLUMN_DESCRIPTION_ENG` (an English description).
Two caveats on the dictionary:
- `COLUMN_DESCRIPTION_ENG` was **generated by a frontier LLM**; only ~10% has been
  expert-validated. It is good enough to *suggest*, not authoritative enough to *decide*.
- `LOOKUP_TABLE_NAME` is the only available proxy for "this coded column references a
  reference table." It substitutes for the missing FK metadata, but it says nothing about
  whether a column is *semantically important* to a given scenario — only that it is coded.
**An existing Service B tool** (`lookup_business_code`) already resolves a term to a code:
given a column and a natural-language term, it finds the column's `LOOKUP_TABLE_NAME`,
introspects that reference table, heuristically identifies its code and description columns,
and runs a `LIKE`-based search of the description for the term, returning matching code(s).
It handles 0 / 1 / many matches with retry logic. This is a **best-effort fuzzy resolver**,
not a guaranteed-correct one.

## 3. The Intent Analyst — current behavior
 
Today the Intent Analyst is a **shallow JSON extractor**:
 
- It uses a flat, generic schema: `scenario_name`, `scenario_type`, `thresholds`,
  `time_window`, `clarification_needed`, `clarification_questions`.
- It has **no compliance/domain awareness**. Terms like "deposit," "large transaction,"
  "high-risk" are treated as raw text.
- It only asks clarifying questions when **basic fields are missing** (e.g. no amount, no
  timeframe).
- It will pass a semantically ambiguous but structurally-complete request straight through
  to Service B.
**Concrete failure that started this:** "Flag customers transacting more than 10k."
This has an amount and an implied window, so the current Intent Analyst considers it complete
and forwards it. But it never resolves whether "transacting" means credit or debit, cash or
wire or ATM, per-transaction or aggregated, etc. Service B then compiles *something* —
technically valid SQL that does not mean what the compliance officer intended. The error is
silent.
 
**Existing mitigation:** when a compiled scenario fails validation downstream, the system
generates an **escalation report to a human implementation team** rather than looping the LLM
or the user indefinitely. So there is already a bounded human failure path in place.

## 4. What "ambiguity" actually looks like (worked examples)
 
The ambiguity is not one kind of thing. Examples that any solution must contend with:
 
- **Direction / instrument:** "transacting" → credit or debit? cash, wire, ATM, online?
  These are dimensions the user *did not mention at all*, so there is no term in the input to
  detect or resolve against.
- **Aggregation grain / measure / window:** ">10k" → per transaction, or summed per customer
  per day? Count or sum? Rolling window or calendar window? Do reversals net out or add?
- **A concept that maps to a predicate, not a value.** "high-risk countries" does **not** map
  to `COUNTRY_CODE = 'high-risk'` — the country lookup answers "which country is code 400,"
  a different question. "High-risk" is a flag that lives in a *different column in a different
  table* (e.g. a `RISK_COUNTRY` flag on an accounts table), reachable via a join. A single
  natural-language phrase can therefore resolve to: a column+value, a boolean flag column, a
  predicate across a join, an aggregation shape, or nothing structural at all.
This last example is central: **there is no reliable, general primitive of the form
"term → (column, value)."** The mapping from a phrase to its schema realization is genuinely
open-ended and requires semantic understanding of both the phrase and the schema.
 
---
 
## 5. The core difficulty
 
The AML scenario space is **open-ended and non-standardized**. Compliance officers define
scenarios ad hoc, not strictly against a fixed set of known typologies (FATF/Wolfsberg
categories, etc.). Any attempt to *enumerate* the space — flat schemas, discriminated unions
by typology, hierarchical registries of typologies → required fields, hand-authored
synonym/mapping catalogs, per-column "required dimension" tags, per-column × per-value
lookup catalogs — is a **finite guess against an effectively infinite space** and will always
have gaps. Building and maintaining any such enumeration is ongoing manual labor with no
natural completion point.
 
Worse, the problem appears to **recur at every layer**. Even if the Intent Analyst were
"solved," Service B faces the same unbounded semantic-mapping problem when it maps terms to
tables/columns/values. This raises the fear of an **infinite chain of semantic layers**, each
needing perpetual manual investment.
 
---
 
## 6. Constraints and non-negotiables
 
Any acceptable solution must respect all of the following. These are the walls previous
proposals kept hitting:
 
1. **No infinite manual enumeration.** No solution that requires hand-authoring (and forever
   maintaining) a catalog of typologies, required fields, synonyms, or lookup values, table
   by table, column by column. A table has 550+ columns; there are many tables; lookup value
   sets are large and uncapped. This is the primary constraint.
2. **Do not push open-ended, real-time reasoning into the stateless downstream microservice.**
   Service B is stateless and should not be looping back to interrogate the user mid-compile,
   nor doing per-column ambiguity reasoning during execution. Wrong service boundary, breaks
   statelessness, no clean bounded failure mode.
3. **The Intent Analyst (Service A) is the intended home for the fix.** This is deliberate:
   a better, less-ambiguous, well-structured plan out of Service A improves Service B's SQL
   *and* its critique node (the critique compares plan vs SQL — a sharper plan makes the
   comparison meaningful). So strengthening the intent layer has leverage over the whole
   downstream chain. This is *why* the fix is being attempted here and not elsewhere.
4. **No reliance on an LLM narrating its own reasoning / implementation plan.** An LLM asked
   to "explain its assumptions" or "output its plan" produces a **post-hoc, potentially
   unfaithful narrative** that is not causally tied to what it actually computes. Any solution
   whose correctness depends on trusting such self-reported reasoning is rejected. (Related:
   asking the intent LLM to predict *how* the SQL will be written is a chicken-and-egg
   problem — at intent time it cannot know the eventual implementation, so it cannot
   pre-resolve ambiguity by "planning the implementation.")
5. **A point-fix is not acceptable.** The originally proposed fix — hardcoding required fields
   like `transaction_direction` and `transaction_channels` to force clarification — was
   rejected. It patches the one scenario that failed today and does nothing for the next,
   different ambiguous dimension that will surface with the next scenario type. The solution
   must be *generalizable*, not a growing list of special cases.

## 7. Approaches already considered and rejected (with reasons)
 
- **Add hardcoded required fields** (`transaction_direction`, `transaction_channels`).
  Rejected: point-fix, non-generalizable (see constraint 5).
- **Taxonomy/typology enumeration** (flat schema, discriminated union by typology,
  hierarchical typology → required-slot registry). Rejected: finite guess against an infinite,
  non-standardized space; guaranteed gaps; perpetual maintenance.
- **Hand-authored synonym / required-dimension / mapping catalog per table.** Rejected:
  infeasible at 550+ columns × many tables; the "required dimensions" metadata does not exist
  and would have to be built from scratch; most columns are coded fields with large/uncapped
  lookup value sets, making full upfront cataloguing impractical; unclear it would even catch
  non-schema ambiguities (e.g. time windows). Also, literal string matching between catalog
  terms and parsed intent terms is fragile.
- **Retrieval-based grounding (embeddings over the dictionary) + treating coded columns
  (`LOOKUP_TABLE_NAME IS NOT NULL`) as candidate "dimensions," resolving values live via
  `lookup_business_code`, with a confidence/margin threshold to decide auto-resolve vs. ask
  vs. escalate, plus a reactive cache.** Considered in depth. Problems raised and unresolved:
  - Retrieval finds a column for a term the **user actually said**; it cannot surface a
    material dimension the user **did not mention** (e.g. "direction" is nowhere in
    "transacting more than 10k"). Detecting under-specification is therefore *not* solved by
    retrieval.
  - `LOOKUP_TABLE_NAME IS NOT NULL` identifies *coded* columns, not *material* ones. It
    over-fires (branch, currency, product, user, etc. are all coded and would all be asked
    about — dozens of irrelevant questions) and can under-fire on legacy columns that are
    codes-by-convention. Structure alone cannot tell you which dimension matters for a given
    scenario.
  - The "term → (column, value)" primitive is wrong in general (the "high-risk countries" →
    `RISK_COUNTRY` flag example): a phrase can map to a predicate/join/flag, not a value.
  - Embedding/`LIKE` retrieval quality depends on description quality, and only ~10% of
    descriptions are expert-validated. Confidence thresholds are uncalibrated and do not
    transfer across terms/models.
- **Have Service B (text-to-SQL) emit an interpretation / assumption trace for confirmation
  before deploy.** Rejected: relies on the LLM faithfully reporting reasoning it may not
  faithfully report (see constraint 4); the trace is a narrative, not a guarantee.
- **Split the problem into "business config (WHAT)" filled by the intent layer over a small
  bounded axis set, vs. "schema mapping (HOW)" left to Service B.** Raised as a possibility;
  the reviewer's standing objection is that this still smuggles in an enumeration (the "axis
  set") and does not, on its own, dissolve the open-ended predicate-mapping problem — i.e. it
  risks being "point 1 again" under a new name. **Treated as unresolved, not accepted.**
---
 
## 8. The open question
 
Is there a **genuinely generalizable, enterprise-realistic** way for this multi-agent AML
scenario-building pipeline to **detect and resolve semantic ambiguity** in user-described
scenarios — against a large, legacy, code-heavy, lookup-table-dependent warehouse schema with
no foreign keys — such that:
 
- it does **not** rely on infinite manual enumeration (of typologies, required fields,
  synonyms, or lookup values);
- it does **not** push open-ended real-time reasoning onto the stateless downstream
  text-to-SQL microservice;
- it does **not** depend on trusting an LLM's self-reported reasoning/plan;
- it strengthens the **Intent Analyst** stage specifically, producing a plan sharp enough to
  improve both Service B's SQL generation and its critique node;
- it degrades to a **bounded, honest failure mode** (the existing human-escalation path is
  acceptable) rather than a silent wrong query or an unbounded clarification loop;
- and it is **generalizable** — not a growing list of per-scenario special cases?
If no such fully-general mechanism exists, a useful answer would state that plainly and
characterize precisely **which parts of the problem are inherently open** (and therefore can
only be contained, not solved) versus **which parts are genuinely finite** — with the
reasoning for the boundary — so the team can decide what to build and what to backstop.
