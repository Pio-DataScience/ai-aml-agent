## 1. A is the target architecture

### Layout and conventions

**VERIFIED** — A is one Python package rooted at `services/aml_builder`, with `web/api` for HTTP/SSE and dependencies, `web/workflow` for typed workflow state/revisions/guards/SQLite repos, `web/domain` for deterministic rules/policy/deployment/versioning/SQL and filter functions, `web/services` for agent orchestration and use cases, and `web/adapters` for Oracle registry persistence. `config/aml_catalogs` contains validated YAML catalogs; runtime prompts are under `web/services/prompts`. The root `requirements.txt` is the single pinned manifest. `PROJECT_OVERVIEW.md` is the canonical design map; implementation is authoritative.

The request path is layered: FastAPI routes and `dependencies.py` validate service identity, then call workflow/domain/use-case functions; side effects are behind Oracle/SQLite adapters or isolated service functions. The graph itself is a single LangGraph ReAct agent with six tools. Tools are LLM-selected, while typed workflow stages, approval gates, parameter confirmation, deployment blockers, identity checks, and conflict checks are server-enforced. A's workflow and deployment patterns are described in `PROJECT_OVERVIEW.md` sections 2-5 and 10; key code is `services/aml_builder/web/api/routes/{chat,workflow,deploy}.py`, `web/workflow/`, `web/domain/deploy_service.py`, and `web/adapters/oracle_repo.py`.

- **Configuration:** `web/services/settings.py` is the Pydantic settings authority; `.env.example` documents supported keys. YAML domain catalogs use `config_loader.py` with validated/mtime-reloaded snapshots. Secrets must remain environment-backed. Preserve `LANGCHAIN_TRACING_V2`, `LANGCHAIN_API_KEY`, and `LANGCHAIN_PROJECT`, including startup propagation to LangSmith aliases documented in A's overview.
- **Errors/logging/tracing:** Routes return typed errors/SSE; the shared `logging_config.py`, `observability.py`, and `io_executor.py` provide the existing observability and bounded executor patterns. Preserve trace correlation and avoid logging raw SQL, prompts, secrets, or customer values. A has residual mixed synchronous integration work, but established blocking paths dispatch through `io_executor`/`async_tools`; do not copy B's sync work directly into async routes.
- **DB access:** `web/services/oracle.py` owns primary/shadow pools and explicit read/write/atomic helpers; `adapters/oracle_repo.py` encapsulates registry-v2 queries and transactional version/status/audit writes. `workflow/repo.py` and `session_store.py` use SQLite per-operation connections. Respect A's primary-vs-shadow distinction and existing table ownership. SQL for production scenarios is guarded and persisted atomically by A's deploy service.
- **Tests:** A has extensive offline pytest files under `services/aml_builder/tests` (domain, workflow, settings, codec/SSE, deployment, versions, filters, conflict and async/runtime behavior), plus a manually-run live Oracle/OpenAI integration script. Do not run the live check for this integration. The overview's verification command identifies offline checks; this investigation did not run them.
- **Run/deploy:** `run_dev.ps1` starts `web.api.main:app` on 8005; `app.py` is another import wrapper. `run_alert_engine.py` is a separate on-demand CLI. A has root requirements and a GitHub Actions workflow according to the current overview; no migration framework is present. The alert engine is an on-demand API/CLI, not an internal schedule.

### Extension points B should use

1. Put route wiring and request/response models in `web/api/routes`; reuse `dependencies.py` identity checks and A's `SSEEvent`/codec conventions. Do not mount B's duplicate root API wholesale.
2. Add orchestration as a narrow `web/services` use case with an injected protocol/adapter boundary. For an in-process implementation, expose an interface such as `ScenarioSqlGenerator.generate(intent, context) -> SqlGenerationResult`; let `tools.py` call that interface. The current HTTP handoff can remain behind the same adapter during staged migration.
3. Put deterministic AML contract checks in `web/domain` and share A's `AMLIntent`, filter resolution, SQLGlot verification, canonical SQL/hash utilities, and window rules. Avoid a second authoritative intent schema.
4. Put metadata/dictionary and Oracle reads behind A services/adapters, embedding retrieval behind an explicit retrieval interface, and all writes behind the existing workflow/deploy/repository owners.
5. Use `settings.py`, `config_loader.py`, `io_executor.py`, `observability.py`, and A's typed exception/SSE conventions. Reuse tracing environment names and tests. A's existing Service B client settings (`PIOTECH_AI_URL`, timeout, user/project IDs) already express this seam.

### Main data flows

1. **A scenario SQL generation:** A sends `request_type=AML_SCENARIO_GENERATION` plus `AMLIntent` JSON to B's `/chat/stream`; B validates intent, enriches context with domain-control-plane prompt and Chroma/Oracle/Neo4j retrieval, LLM proposes SQL/tool calls, Oracle executes candidate, result rows/columns plus structured intent and joins go to a separate critic LLM, deterministic checks enforce `CUS_NUM`, requested transaction-code filter and limited day-window syntax, and approved SQL is returned in SSE. A then does its own shadow-test/metadata/approval/deployment workflow. No SQL is persisted to A's scenario tables by the B scenario-agent path.
2. **Generic DWH/AML/Collection/Cockpit chat:** request/SSE API derives a thread identifier, persists LangGraph state in SQLite, invokes a service-local agent that searches vector indexes/metadata and invokes Oracle read queries; returns final narrative, data previews and optional output files. AML injects domain-specific scope/semantic/SQL guards; collection and cockpit use their own prompts and routing data. Some output previews/files and prompts may contain sensitive query results.
3. **Index/data maintenance:** harvest Oracle dictionary -> local JSON/JSONL; enrichment scripts may call LLMs and update Oracle descriptions; scripts build Chroma hierarchical table/column and experience indexes and Neo4j join graphs; training scripts produce model artifacts from execution logs/golden examples. These are maintenance/owner-operated tasks, not chat request dependencies.
4. **Long query/export:** agent estimates query runtime from Oracle explain plan plus `shared/artifacts/query_execution_log.db`; over-threshold work can be enqueued to Redis/Celery; worker executes SQL and batches rows to files. The export module streams Excel in batches with a 50k row cap. Whether API reachability really enqueues Celery is **UNKNOWN** from inspected handler path without executing; the code advertises `/jobs` polling and has a worker task.
5. **Speech:** browser uploads bounded audio or opens a websocket stream; auth/origin and session limits are checked, local faster-whisper engine transcribes configured English/Arabic and optionally forwards uploaded recordings to OpenAI transcription. Transcript logging defaults off in `speech_service/config.py`.

## 4. Overlap, conflict and production-write risk

### Duplicated functionality

- **Config and Oracle:** B has one Pydantic settings module and Oracle module per service, plus separate Neo4j settings. A already has authoritative `Settings`, YAML catalog loading, primary/shadow Oracle pools, SQL read/write boundaries, and observability. B copies are replaceable except its domain query methods.
- **LLM/embedding:** A has `build_llm`, parsing and LangSmith propagation. B has provider-global SDK clients, separate model/embedding settings, direct `ChatOpenAI` construction in critique, per-provider timeouts/retries, and its own local/OpenAI/Cohere embeddings. Consolidate provider selection/timeout/tracing in A; keep only a provider protocol for B retrieval.
- **Schemas and prompts:** A owns `AMLIntent`, parameter/filter cards and SQL handoff. B's `ServiceAIntent` allows extra fields and recognizes a reduced subset of intent data (no authoritative resolved filter contract); its own Pydantic chat/SSE/session models duplicate A. B prompts contain AML rules, but cannot replace A's deterministic guards.
- **DB and state:** A uses service-managed SQLite state paths and Oracle pool/repository boundaries. B uses relative `checkpoints.sqlite`, SQLite `SqliteSaver`, session table in the same DB, plus additional relative/shared `artifacts`/`data`/`static` paths. Root/run/docker layouts may point these paths differently. Keep B conversation history out of A workflow state; A already owns checkpoint and app-state stores.
- **Routes and ports:** Both expose `/health`, `/chat/stream`, chat history/list and session mutations; B adds `/feedback` and `/jobs`. A listens on 8005; B scenario agent defaults to 8006; root compose's speech is 8010 and generic services use 8001-8004. A's Service B default is 8006, consistent with `run.ps1`, not root Compose.
- **Logging/tracing:** B has its own rotating logging setup and verbose LLM/message previews; some test code explicitly disables LangChain/LangSmith env vars. A explicitly supports `LANGCHAIN_TRACING_V2`, `LANGCHAIN_API_KEY`, `LANGCHAIN_PROJECT` and aliases. Preserve A's trace contract while redacting sensitive values.
- **Imports:** each service inserts its root into `sys.path` and imports bare `web.services.*`. This works when each app runs in isolation but risks module-cache collisions if B's apps are imported/mounted together with A or one another. Integration needs unique fully qualified packages and dependency injection, not sys.path tricks.
- **Versions:** 39 overlapping exact-pinned packages differ; an A `requirements.txt` environment cannot be assumed compatible with B. Heavy B local-embedding packages would increase image size/start time and conflict risk. Resolve Python/package compatibility for A's pinned LangChain 1.3/LangGraph 1.2 stack by characterization, not by downgrading A to B.

### High-risk writes and legacy data

| Target | Operation in B | Risk / treatment |

| Oracle business schemas, including `BI_DWH` | Runtime candidate SELECT and background query task; AML/DWH agents can retrieve transaction/customer data. | Query is initiated by LLM/tool request; enforce SQL AST allowlist and schema/table policy in server code, not only prompt or leading-token checks. Check via read-only `ALL_TABLES`/`ALL_SYNONYMS`/grants and deployment mounts under DBA/operator supervision; do not run code that writes.

## 5. B resilience, quality and security audit

Findings below are static observations, not reproduced runtime failures.

- **Blocking async:** B's FastAPI routes are `async`, but Oracle helper `run_readonly` is synchronous; API sends graph `.stream(...)` through a local thread wrapper (better than direct event-loop blocking), while LLM/critic and parts of tools remain synchronous. Oracle worker code directly opens sync connections. Thread count/backpressure is not consistently bounded as in A's `io_executor`.
- **Timeouts/retries:** Oracle helper doesn't set explicit query/call timeout in visible code. Most `OpenAI`/Cohere client creation has no explicit timeout; one OpenRouter client has 60s/2 retries and embedding providers use ad-hoc retry loops. No shared retry budget, cancellation, circuit breaker, or per-provider timeout contract was found. Retrying non-idempotent feedback or metadata writes would be unsafe.
- **Failure semantics:** startup catches Oracle/model/Chroma failures and continues, so `/health` may say healthy when critical SQL generation is unavailable. Broad `except Exception` blocks are common; some paths return fallback strings/empty lists, and logging often includes exception/SQL context. Critic API errors fail closed for the scenario handoff (positive), but generic routes/tools have different contracts.
- **Resources:** API `init_session_db`, session CRUD, and some execution-log paths manually connect/commit/close without `with`/`finally`; error paths can leak SQLite handles. Main Oracle helper uses pool-acquired context managers, while Celery has cleanup in `finally`. Neo4j/chroma process-global clients don't have a clearly coordinated shutdown path. Startup creates directories and deletes stale exports (side effect if run).
- **Memory/performance:** each module can warm large torch/sentence-transformer models; scenario `manage_memory` estimates tokens by `str(messages)/4` and halves history with an LLM summary, but full checkpoint history still accumulates. SQL tool fetches all returned rows in some agent paths and writes CSV; in-memory Chroma retrieval/results/feedback may grow. Celery uses 10k row batches, while Excel streams 2k batches and caps 50k. Multiple identical services multiply model/DB/index caches. Explain-plan + count/full candidate execution can be expensive; query estimator failure path is not a robust governor.
- **Input and SQL validation:** Pydantic chat models validate basic shape but body fields/length/content/image size are permissive. SQL sanitizer is string/leading-token based (read-only check can be bypassed by SQL constructs if not parsed); `WITH` queries are accepted and dynamic schema/table names are assembled in tools. Scenario-specific `CUS_NUM`, `EXPL_CODE` and date checks are useful but regex-based; baseline check covers a narrow day-window formula and not all supported units/filters. LLM critic remains probabilistic. Task worker executes given SQL directly without re-checking allowlist.
- **Auth/CORS:** B web APIs visibly allow wildcard CORS with credentials and identify user/project/chat from request body/path; no A-like BFF service-token/identity dependency is apparent. `/jobs/{job_id}`, feedback, history and session operations need ownership checks/rate limits review. Speech is stronger: API keys compared constant-time and input/session sizes bounded; origin check allows absent Origin by design and auth can be disabled by local run launcher.
- **PII/external model calls:** user request, AML intent, schema context, sampled values, query results and critique payload are supplied to configured LLM providers; B supports hosted OpenAI/Cohere/SambaNova/OpenRouter plus local LM Studio. There is no visible central PII minimization/redaction control. Agent logs message previews and can save query output to CSV, report JSON and exports. Speech can upload audio to OpenAI when configured; transcript logging defaults off. Confirm model provider/data residency and retention before use with production customer data.
- **Secrets/config:** B has a root `.env` present in checkout (values deliberately not inspected), provider keys and Oracle/Neo4j credentials are configured through env; `settings_graph.py` has a development-looking default Neo4j password. Do not copy real env files or generated data. Check secret scanning/rotation independently; repository static analysis did not print secret values.
- **Tests:** scenario-agent has one focused Service A contract test file, AML has several guard/typed-intent tests and live accuracy harnesses; many API/DB/timeout/resource behaviors are untested offline. No test was run during this read-only audit. Build pure fixture tests with mocked Oracle/LLMs and no credentials before refactoring.
- **Logging/traces:** long prompts and user content are logged at INFO in portions of agent; B settings and API log DSN/user. SQL errors may be returned in tool results. Preserve LangSmith traces in A but redact customer data and apply trace sampling/retention before enabling in production.

## 6. Proposed target integration design

### Target structure inside A

```text
services/aml_builder/web/
  api/
    routes/                    # existing routes own auth, SSE, workflow, deployment
  domain/
    scenario_sql_contract.py   # deterministic SQL/intent constraints (A AMLIntent)
    schema_retrieval.py        # pure retrieval ranking/allowlist contracts if suitable
  services/
    scenario_sql_generator.py  # use case: intent + confirmed filters -> generation result
    sql_generation/
      orchestrator.py          # state graph, bounded attempts, critique gate
      tools/
        schema_search.py
        dictionary_lookup.py
        join_lookup.py
        sql_executor.py        # calls A Oracle adapter/shadow policy, AST allowlist
      prompts/                  # versioned AML generation and critic prompts
    adapters/
      dwh_sql_generator.py      # temporary HTTP adapter; later in-process provider
      schema_index.py           # Chroma/alternate retrieval adapter (if retained)
      graph_catalog.py          # optional Neo4j adapter (only if measured benefit)
  adapters/
    oracle_repo.py              # extend/read methods only; writes remain explicit/atomic
config/aml_catalogs/            # existing validated AML contract remains canonical
```

`scenario_sql_generator` should accept a validated A `AMLIntent` plus resolved filter/version context, and return a typed result containing SQL, execution status/columns/row count, validation findings, provider/model metadata, and safe diagnostics. Tool execution must be read-only and schema-scoped, perform bounded result sampling, and require the exact SQL being returned to be the exact SQL executed. A's deployment service remains the only scenario persistence path. No B API route/session/checkpoint copy is proposed.

### Shared service vs separate product modules

- Shared in A: settings/provider configuration, tracing/logging, Oracle pool/repository, query policy/read-only execution, schema metadata abstractions, bounded I/O, typed errors, history/SSE and tests.
- Separate internal module: scenario-specific DWH SQL retrieval/generation/critique. Keep graph/prompt/tool details out of A's workflow route and `tools.py`; its tool surface is a single generator use case.
- Optional and separately deployed: speech, only if product wants speech inside A UI. It should remain a service boundary and not add Whisper/PyTorch to A's main dependency closure.
- Out of scope absent product confirmation: generic DWH, cockpit, collection, ML training, background report/export, feedback learning, bulk glossary enrichment. These are separate products/data operations, not required for scenario SQL handoff.

### Dependency and config consolidation

1. Keep A root manifest/settings as authority; bring in only runtime dependencies proven by target generator closure. Chroma/Neo4j/local embeddings are optional adapters, not mandatory if A's current catalog/retrieval meets acceptance.
2. Upgrade/compatibility resolution belongs in one A requirements change after offline contract tests exist. Do not pin A down to B versions. Identify transitive conflicts and Python version support for torch/chromadb before adopting local models.
3. Add explicit `DWH_SQL_*` settings (provider mode, endpoint, timeout, max attempts, max candidate rows, allowed schemas, model policy) to A Settings; keep existing `PIOTECH_AI_URL` as temporary adapter alias/setting and preserve `LANGCHAIN_*` tracing.
4. Centralize retry, deadlines, concurrency and request cancellation. Read operations may retry only classified transient failures within an end-to-end budget; no retry for writes unless an idempotency key makes it safe.
5. Prompts/catalogs are versioned behavior; add fixtures to verify A `AMLIntent` serialization and provider response decoding. Keep B-owned config out of process-global `.env` bootstrapping.

## Risks, unknowns and owner questions

1. **Product scope:** Is the target only B's DWH Scenario Agent capability that A currently calls, or should A absorb generic AML analytics, DWH, collection, cockpit, exports/jobs and speech too? The latter is a multi-product consolidation, not one SQL generator package.
2. **Deployment truth:** Which service/compose manifest and image is running in each environment? Is port 8006's `services/dwh_scenario_agent` current production, and are root/deploy/legacy compose files inactive?
3. **Oracle contract:** DBA-confirm exact owners/synonyms/grants for dictionary tables, `PIO_AML_TABLES/COLUMNS`, `PLAN_TABLE`, A registry and alert tables. Confirm candidate SQL must be read-only in `BI_DWH` and whether explain-plan writes are permitted.
4. **Data protection:** Which LLM/embedding providers are approved for customer/business data? May prompts, sampled columns, result previews, audio, SQL and LangSmith traces leave the bank network? Define PII redaction and retention requirements.
5. **Retrieval assets:** Are checked-out Chroma/Neo4j/artifact data current, reproducible and licensed for redistribution? Can A's DWH metadata source replace them? The report intentionally treats artifacts as data, not source.
6. **Latency/capacity:** Production request volume, Oracle session limits, accepted query budget, local model RAM/GPU budget, expected index size and SLO are not established by code.
7. **Contracts:** Is `CUS_NUM` alone still the Service A output contract, or must transaction evidence columns also be returned? Which filters/baseline/date units and code-binding semantics must be exact? Does UI depend on B's `thinking`, tool-call, `/feedback`, `/jobs` or chart events?
8. **Legacy systems:** Are PIO dictionary enrichment, golden-dataset feedback and checkpoint migration still supported workflows? Who owns their data lifecycle and rollback?

## Executive summary (15 lines max)

- B has 256 tracked Python files across six service trees; only about **15-25 modules** are plausibly needed for A's current B handoff (inference: roughly 6-10% of B Python files), plus curated prompts/catalog metadata and reproducible retrieval assets if needed.
- Core needed surface: scenario contract, DWH schema retrieval/tools, SQL executor, bounded generation/critique graph, and focused offline contract tests.
- Keep the speech service optional/separate; generic DWH/AML/collection/cockpit and maintenance/training stacks are not prerequisites for A's scenario flow.
- Top risks: (1) permissive B API trust/CORS and SQL policy boundary; (2) LLM exposure of AML prompts/results/PII; (3) B Oracle `PLAN_TABLE`/dictionary writes; (4) 39 shared dependency pin conflicts and heavy optional stacks; (5) divergent duplicated deployments/import roots and stale state/artifacts.
- Recommended first package: **P0 characterization tests** for B's Service A handoff, using fake Oracle/LLMs and the existing B contract test as the baseline; no runtime or database change.
